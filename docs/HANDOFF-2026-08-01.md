## 2. The one thing that broke today, and why it matters

Collection **stopped for 3.5 hours** (16:00–19:30Z). Every cron failed with
`exceededResources` at `cpuP99 = 10,000 µs` — the free plan's **10 ms CPU
ceiling**.

Three lessons worth carrying:

1. **The binding constraint changed and nobody noticed.** This project was
   designed around the 50-subrequest ceiling. Shards were sitting at 20 of 50
   while CPU was pinned at the limit. The constraint everyone is watching is
   rarely the one that bites.

2. **The alerting could not fire.** Every alert added earlier
   (`unknown_rate_high`, `subrequest_budget_exhausted`, headroom) runs *inside*
   the scheduled handler. An invocation killed for exceeding CPU never reaches
   them. They are structurally incapable of reporting this class of failure —
   the same blind spot as `wrangler tail --status=error` against a collector
   designed to fail closed *without throwing*.

3. **The only detector that worked was the staleness banner** — i.e. a human
   looking at the page on his phone. That is the honest summary of the current
   monitoring posture and the biggest open weakness.

### Diagnosis technique that worked

`wrangler tail` was useless (it does not reliably surface cron invocations).
Cloudflare's GraphQL analytics named it immediately:

```
workersInvocationsAdaptive(filter:{scriptName:"vendor-dashboard", ...}){
  sum{requests errors} dimensions{status} quantiles{cpuTimeP99}
}
```

`status=exceededResources` + `cpuTimeP99=10000` is the signature. Use this
first, not the tail.

## 3. Architecture facts a fresh session needs

### Sharding (the load-bearing mechanism)

- `SHARD_COUNT = 15`, cron `* * * * *` (every minute) → **each service is
  re-checked every 15 minutes**.
- **`shards × cron interval = the per-service refresh period.`** This product IS
  the promise on the page and is pinned by a test. Raising `SHARD_COUNT` does
  not add capacity, it lengthens the period — 60 shards would mean hourly.
  1 minute is Cloudflare's finest cron granularity, so **15 is the ceiling**
  while the promise stands at 15 minutes.
- Shard assignment is a **name hash**, overridable per vendor with `shard`.
  Pins exist because vendors are not evenly *expensive*: AWS, IBM, Oracle,
  Concur and NetSuite parse large documents and must be kept apart.
- An **empty shard is legitimate** (handler skips it and logs `shard_empty`);
  `collect()` still refuses an empty vendor list, which is a different guard.

### CPU budget, measured

Worst shard across today:

```
85.77 ms   Concur parsing 23.3 MB
 7.64 ms   after Concur → status_history
 6.94 ms   after rebalancing + isolating IBM and Oracle
```

`npm run perf` measures **per-shard parse CPU** and fails above 4 ms. It
measures parse only — an earlier version timed against the live network and
reported 50–400 ms of Node TLS/HTTP work, a permanently-red gate.

**Residual risk:** production `cpuP99` sits around 11.7 ms and succeeds only on
Cloudflare's tolerance for occasional overruns. There is little headroom. The
clean fix is **Workers Paid** ($5/mo: 10 ms → 30 s CPU, 50 → 1,000 subrequests),
which would make most of today's engineering unnecessary.

### Endpoint discovery technique

Three vendors' real endpoints appear in **no static asset** — they are built at
runtime. Found by loading the status page in a browser and reading the network
log:

| Vendor | Endpoint | Note |
|---|---|---|
| IBM Cloud | `/status/getEnhancedStatus` | 2.44 MB; targeted scan, not `JSON.parse` (8.03 → 1.82 ms) |
| Concur | `/api/open/status_history?data_center=…` | replaced a **23.3 MB** incidents feed; no filter param exists |
| AWS | `servicedata-…s3.amazonaws.com/services.json` | catalogue, now a **build-time snapshot** |
| Stormboard | `/sections` | JSON-wrapped HTML; state read from the icon *filename* |

Grepping bundles is not sufficient. Neither is guessing paths.

### Traps that cost real time (do not re-tread)

- **`status.bing.com` and `status.telegram.org` are wildcards** — they return
  200 with a full page for *every* path, including `/api/v2/summary.json`.
  `core.telegram.org/api/status` is a **soft 404** (200 + "Page not found").
  A probe checking only the status code would add a permanently fabricated row.
- **Telegram has no first-party machine-readable status.** Every source is a
  third-party aggregator, and this project removed StatusGator deliberately.
- **AWS `currentevents` is UTF-16 with a BOM.** `response.text()` decodes as
  UTF-8 per spec and yields mojibake; `decodeBody()` in `collect.js` sniffs it.
- **Global regexes keep `lastIndex`.** Left set, the *second* collection of the
  day returns nothing. Bit both the IBM and AWS adapters; both now tested.
- **Backticks in a CSS comment terminate the template literal** in `render.js`.
  Documented in the file; hit again today.
- **`cp` and `rm` are aliased interactive** — use `command cp` / `unlink`.

## 4. Recurring failure pattern (the thing to actually fix)

Six defects today shared one shape: **a check that could not observe the failure
it was supposed to catch.**

- mocked `db.batch()` could not fail on invalid SQL → a syntax error shipped
- `--status=error` could not see a fail-closed collector
- in-handler alerts could not fire when the invocation was killed
- a first-sentence excerpt could not carry AWS's meaning (boilerplate first)
- the renderer silently dropped every component `description`
- one post-deploy reading could not detect an intermittent, cycle-dependent bug

Before trusting any green check, ask: **if the thing I care about were entirely
broken, would this specific check change?** If not, it is decorative.
