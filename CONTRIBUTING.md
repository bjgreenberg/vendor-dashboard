# Contributing

Thanks for your interest. This project has one governing rule, and every
change is measured against it:

> **An unverifiable status is `unknown`, never `operational`.**
> A green row must mean something was actually verified.

## Dev setup

```bash
npm ci
node scripts/fetch-logos.mjs   # vendor marks are a build artifact, not repo content
npm test                       # full suite, ~1 s, no network
npm run lint
npm run test:coverage          # the same gate CI enforces (per-file floors)
```

Tests run against recorded fixtures with an injected clock — if your change
needs the network to test, the design is wrong (see the engine/worker boundary
below).

## The one boundary that matters

`src/engine/` is **pure**: no Worker, Node-specific, or platform APIs —
`fetchFn` and `now` are injected. `src/worker/` holds the Cloudflare bindings.
Do not import a platform API into the engine; that separation is what makes
every adapter testable against fixtures and the engine portable.

## Adding or changing a vendor adapter

1. Capture the vendor's real payload into `test/fixtures/` (public,
   unauthenticated endpoints only).
2. Pin the adapter's output against that fixture. Every failure path returns
   `unknown` — null payloads, malformed payloads, unrecognized status
   vocabulary, non-200s. Never a bare word-match against HTML (see
   `docs/audit/` for how that went).
3. Add the vendor to `config/vendors.json` (never hardcode vendors in source)
   and declare its `brandDomain` so the logo pipeline can find its mark
   (or an explicit `iconUrl` when favicon discovery can't produce the right
   one — mind the image's licence; attribution belongs in the config comment).
4. Mind the parse cost: `npm run perf` measures per-shard parse CPU against
   a 150 ms regression envelope, and CI enforces it. The plan ceiling is 30 s
   (Workers Paid), but a parser that needs a fraction of that is doing
   something wrong — prefer targeted scans over full JSON.parse on
   multi-megabyte payloads; expensive vendors get pinned to their own shard.

## Pull requests

- Conventional Commits (`feat:`, `fix:`, `chore:`, …) — commit type drives
  the automated release.
- Required checks: `test` (suite + per-file coverage floors + `wrangler
  --dry-run` + `npm audit`), `lint`, `secret-scan`, `cff-validate`,
  `docs-render`. All must be green; merges are squash-only.
- Update docs **in the same commit** — README, diagrams, and comments that
  describe what you changed. A stale diagram is treated as a wrong one; every
  Mermaid block must render (the `docs-render` gate enforces this).
- Never hand-edit `CHANGELOG.md`'s generated sections or hand-tag a release —
  release-please does both (see [MAINTAINERS.md](MAINTAINERS.md)).
- Do not commit vendor logo files; the icon directories are gitignored and
  regenerated by `scripts/fetch-logos.mjs`.

## Security

Suspected vulnerabilities go through a
[private security advisory](https://github.com/bjgreenberg/vendor-dashboard/security/advisories/new)
— never a public issue or email. See [SECURITY.md](SECURITY.md).
